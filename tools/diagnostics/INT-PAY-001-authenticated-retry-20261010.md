# INT-PAY-001 — Authenticated server idempotency integration test

**Execution:** 2026-10-10; Briskers Dev Supabase project. **Result: PASS.** This is a one-off authenticated database integration test, *not* an automatically executed device diagnostic.

## Isolation

Test executed in a PostgreSQL BEGIN/ROLLBACK transaction. Temporary customer, $500 draft invoice, configured Cash method, existing authorized owner context. Customer and invoice were identified as diagnostic-only. No payment was finalized or income posted.

## Assertions verified

- First call to `public.briskers_add_pending_invoice_payment_once` created one pending $500 payment.
- Repeating the same business/invoice/method/amount/operation UUID returned **the same payment ID**.
- Database contained exactly one pending payment totaling $500 for the test invoice.
- Reusing the same operation UUID with a changed $400 amount was rejected.
- Creating a new $1 payment when the invoice balance was already fully recorded was rejected.
- Transaction rolled back. Follow-up SQL showed **zero diagnostic customers, zero diagnostic invoices, zero operation-key rows**.

The initial fixture needed two adjustments: total_amount is generated by the database; issued documents require a permanent document_number, so the isolated invoice used draft status.

## Not covered by this result

Simultaneous concurrent sessions, real network drop/ambiguous ACK, device-side replays, pending-to-finalized posting, printing/PDF, payment-method variety, and second-device sync still require separate tests.
